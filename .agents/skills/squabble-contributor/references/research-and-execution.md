## Research reports → sealed research → immutable report

Read and identical create replay never dispatch work. The immutable `overallDaily` marker separates these reports from ordinary research and automatic strategy/channel handoff. Native recovery retains existing task/result fences. Recovered independent messages and token usage publish once. See `docs/v4-daily-and-memory-workspace.md` for routes and exact boundaries.

V4 authoring is separate from research dispatch. `StrategyInterviewService` persists fixed owner/account, exact user wording, suggestions, explicit acceptances and revisioned receipts. Pure parsing leaves ambiguous conditions unresolved; action-side conflicts cannot be stripped away. Changing a premise invalidates the dependent answers and preview. A revision of an installed strategy keeps its immutable parent and is staged disabled in only the selected account's draft; stale policy drafts require explicit re-review.

Explicit `price_lt` and `price_gt` remain strict through final execution; missing legacy frequency means once. `user-strategy-frequency.ts` shares verified exchange-day, fill and reservation guards between candidate claim and final account-locked order checks. Daily permission must be explicitly present in user-authorized text; model preparation cannot add it. Rebuilding a profile does not clear execution history. Starting origins are real holdings, virtual cash, owned simulation snapshot or custom positions; only real-origin confirmation compares the current real ledger, while copied/custom snapshots remain frozen.

## Channel publication is a separate pipeline

The current `/council` UI reads `/api/channel?accountId=...`; daily research transcripts are not its feed. `ExperienceScheduler` reconciles research, synchronizes published daily reports, ticks briefs and monitors owners. The durable publication types are in `shared/channel.interface.ts` and tables in `server/database/channel.schema.ts`.

Two source paths converge at a publication gate:

1. **Compiled brief:** `ChannelBriefsService` compiles current published report artifacts into registered templates. It checks report/version validity, same-day context, expiry and current strategy revision. Price-cross conditions require sourced typed thresholds and a resolved ticker; no ticker/threshold is inferred from prose. Dispatch is deterministic and does not start a model request.
2. **Background finding:** `ChannelService.ingestFinding` validates owner, episode, exact anchor, material semantic delta and evidence card through `sealFinding`. The server seal includes payload hash, dependency digest and compiler version. `no_counterevidence_found` cannot publish a finding; `unable_to_verify` requires a new material gap. Arbitrary model claims or an `approved` field cannot substitute for this seal.

`publishTemplate` or sealed finding rendering then passes `canPublish`, template/slot validation, freshness/correction checks and deduplication. `commitBubble` persists bubble, episode advance, applicable memory and `channel_outbox` rows in the same transaction. `poke` queues stream and notification destinations; lesser weights queue stream. This is durable application delivery, not a claim of exactly-once external notification receipt.

`channel-runtime.ts` and `channel-executions.ts` project the selected account, all enabled assignments and actual simulated executions. Multiple non-archived accounts require explicit selection; selecting is read-only and does not run recovery or create preferences. Shared research stays visible while account bubbles/pending items/notifications are filtered. Monitoring iterates accounts, keys events by account/strategy/revision/entry, and rechecks effective rule membership under the owner fence at publication. Fill links and receipts retain account and original strategy-entry identity. The UI must not imply a configured strategy is active or a signal is a fill. Channel actions are idempotent user decisions/navigation; they do not replace `/api/ai-investment/apply-strategy`. Questions use a bounded single-tool fact-check path, with deferred questions and interruption recovery, not an automatic full debate.

Personal memory also has provenance: `channel-memory.service.ts` saves an explicitly selected user's exact quote. System snapshots, absent adoption reasons (`unrecorded`) and later user reflections are distinct. Do not infer a user's reason or psychological state from strategy outcomes.

Fact questions persist the selected `accountId` and original research context in their request receipt and deferred items. Simulated cash/positions read that owned account's ledger; an unscoped request retains recorded real-ledger semantics. Retry keys cannot be retargeted to another account, and deferred questions inherit their original scope. The pending drawer is account-scoped and excludes the already pinned item. Public research logs and report versions remain owner-wide and are labelled separately. Old home report/strategy links redirect to their exact retained content.

## Real asset ledger and imports

Real assets are recorded in holdings, transactions, closed positions and cash accounts. Screenshot holdings batches (`server/modules/import/import-batches.service.ts`) and transaction-file batches (`transaction-imports.service.ts`) are distinct operations. Both expose preview/commit flows in `server/modules/import/import.controller.ts`; preview is not commit.

Transaction imports classify broker/source identities and fingerprints, return batch and ledger revisions, and commit selected eligible rows only after rechecking both revisions under an owner lock. They call `TransactionsService.createInTransaction`, preserving source batch/raw-row provenance without nested commits or synthetic deposits. Insufficient cash and baseline/history conflicts need explicit correction; do not silently create cash to make an import pass.

`server/database/asset-ledger.schema.ts` stores position baselines and cash-confirmation receipts. Screenshot commits use `server/modules/import/position-checkpoint.ts` to record the checkpoint and covered ledger rows. `TransactionsService` reconstructs positions around baselines and protects already reconciled cash history. `CashAccountsService.confirm` uses request keys and expected update timestamps and records which transactions a confirmation covers. The retained paired cash-top-up endpoint represents a separate explicit user request; ordinary transaction/import paths must not inherit it.

`PortfolioMetricsService` reads recorded assets, quotes, FX and value points for the retained Today projection. The current overview instead reads saved points through `PortfolioComparisonService`. Keep source/time/coverage visible: recorded balances are not broker synchronization, quote retrieval is not exchange-live execution, missing FX/data is not zero. Import-to-research handoff in `server/modules/experience/import-analysis-handoff.service.ts` freezes analysis requests; it is not trading authority.
